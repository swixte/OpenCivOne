Redesigning the screens beyond the map

The pictures are nearly all painted. What still looks like 1991 is the chrome around them: the pixel font, the flat boxes and the 320×200 layouts. This plan inventories every non-map screen, sets out a three-layer approach, and lists the concept sheets to generate first.

Read from swixte/OpenCivOne, branch hd-fallback-layer (last commit 12 Nov 2026), docs/art-inventory.md, docs/hd-art.md and docs/art-exploration/ukiyo-v4, v5.

Where things stand

The art is done; the screens are not

102 / 106pictures have ukiyo-e files in themes/ukiyo-e/hd. Only MAP, TORCH, SPRITES and TER257 are missing, and the painted map replaces TER257.
8 coloursof interface are already re-mapped in hd/ui/colors.txt: sumi ink, indigo, madder, vermilion and cream, plus paper grain from material.png.
0 screenshave a new layout or typeface. Every menu, report and dialog is still drawn in the original pixel font, at the original positions.

The engine makes this tractable. All text goes through one call, GBitmap.DrawString(text, font, rect, …), and boxes go through the fill and frame routines that material.png already hooks. Each screen is a single function that draws and reads input, for example CityWorker.F0_1d12_0045_ProcessCityState. That gives three clean places to intervene.

Concept approach

Three layers, from cheapest to deepest

Layers A and B change every screen at once without moving anything. Layer C is a real redesign, so it is kept to the few screens players spend the most time in. Each layer works without the next one, and each falls back to the original when a theme does not supply it, as the HD layer does today.

A

HD type

Draw each of the game's bitmap fonts with an HD typeface at 4× instead of the upscaled pixel glyphs. This is the biggest single change to how the game reads, and hd-art.md lists it as a known limit today.

  • One hook in GBitmap.DrawString, plus a theme file mapping each font ID to a face and size (hd/ui/fonts.json).
  • Glyphs are set inside the original advance widths, so no layout can overflow. That favours a slightly condensed serif. Titles get a woodblock display face, and body text gets a plain readable serif.
  • Text colours keep their palette index, so colors.txt and menu highlights keep working.
B

Chrome kit

A small set of 9-slice frames and components in the print language. They are drawn wherever the code draws a box, so every dialog, report and menu gets them at its current size.

  • Paper panel, indigo panel, hanging-scroll dialog with rollers and cord, unrolled menu scroll, vermilion seal button, title cartouche, wave-band divider, stamped progress bar.
  • Frame geometry such as key lines and corners is drawn in code. Textures, ornaments and seals are generated art, which keeps the kit crisp at every size.
  • Reports drop their per-advisor EGA background colours and share one ledger look on paper, each with its advisor's portrait from GOVT*.
C

Rebuilt anchor screens

New layouts drawn natively at 1280×800 from game state, with the same commands, keys and clicks. A theme opts in with something like "screens": { "city": "ukiyo" }, and without it the original function runs.

  • City screen. It is where players spend most of their time, and its 320×200 layout is the most cramped.
  • Science. Choosing research, the science report and the discovery announcement, as one family.
  • Front end. The title and main menu, then the new-game sequence: difficulty, competitors, tribe, leader name and world customisation.

What to generate first

Four concept sheets, then the production art

The v4 sheets were made with docs/art-exploration/scripts/concept_v4.py, which uses the OpenAI Images API with earlier screens as references. Round v6 uses the same script and the v5 references (refs/v5-screen.jpg, refs/v5-palette.jpg), plus the v4 UI sheet so the kit stays consistent. Each prompt lists the screen's real content from the code, so the sheet can be built as drawn. I would make three takes of each sheet and pick one.

1 · City screen v6

  • All panels the code draws: citizens with specialists, food, shield and trade rows, the 21-square city map, buildings with sell, units present and supported, food box, production box, pollution, plus the seven buttons
  • One layout at 1280×800, and one crowded case with a size-16 city and 12 units
  • Culture-neutral subjects in the print technique

2 · Science

  • Choose research as an unrolled scroll with the science advisor and 3 to 4 options
  • Science report as a lineage of advances already known, with the current research and its progress
  • Discovery as an ICONPG picture in a print frame with a seal

3 · Front end

  • Title with LOGO and a menu on the paper, not in a grey box
  • Difficulty with the five crowns, tribe choice with banners, world options with the four CUSTOM choices
  • Leader name entry

4 · Kit sheet

  • Every layer-B component at 1×, plus one dialog, one report and one menu built from them
  • Type specimen of the 2 to 3 candidate faces at game sizes, set in the original advance widths
  • Greyscale copy for contrast, as v5 did

After a direction is picked, the production art follows the existing pipeline. A new ui kind in tools/hdart/theme.py gets its own rules and references in theme.json. Ornaments, seals and textures are generated on magenta and cut out, as objects are today. Frames are assembled in code from those pieces. Fonts come from open-licensed families, not generation.

Sequence

Order of work

  1. Concept round v6

    The four sheets above, three takes each, reviewed against the inventory so nothing the code draws is missing.

    Done when a direction for each sheet is chosen and written into docs/art-exploration/ukiyo-v6/README.md.

  2. Layer A: HD type

    Font hook in GBitmap.DrawString, fonts.json in the theme, and a pass over every screen in the table using the stand-in data set.

    Done when no screen shows the pixel font and no text overflows its original box.

  3. Layer B: chrome kit

    9-slice frames on the box routines, one ledger look for the reports, and an Avalonia style for the load and message windows.

    Done when every row marked B renders with the kit, and turning the theme off restores the original exactly.

  4. Layer C: city screen

    Native layout behind the theme flag, driven by the same state and commands as ProcessCityState.

    Done when every action on the original city screen works from the new one with the same keys.

  5. Layer C: science, then front end

    Same pattern, reusing the kit and the screen framework from step 4.

Open decisions

Needs a call before step 2

  • How far layouts may move. The README accepts deliberate departures from the original. Layer C is the first that changes what is on a screen, not only how it looks. Does it stay a theme-only option, or become the default?
  • Upstream or fork only. Layer C adds sizeable new screen code beside a careful port. If the goal is to send work upstream to Codeberg, layers A and B are much easier to land.
  • Typefaces. They must be open-licensed and fit the pixel font's widths. Candidates go on kit sheet 4, and the choice affects every screen.
  • Generation budget. The pipeline calls the OpenAI Images API with your key. Round v6 is about 12 images. The kit and screen art afterwards is a few dozen more.
